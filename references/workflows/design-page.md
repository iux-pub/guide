# design-page

> **언제 쓰나** — INFOUX 기준으로 새 페이지, 화면, 랜딩, 상세, 목록, 관리자 화면을 설계하거나 구현할 때 사용. 코드 작성 전에 사이트 유형, 사용자 핵심 과업, page shell, section 패턴과 재사용 컴포넌트를 확정한다.

페이지 코드를 바로 작성하지 않는다. 먼저 `contracts/task-contract.md` 형식으로 Task Contract를 선언한다.

## 절차

1. `references/project-profiles.md`에서 사이트 유형과 기본 section 흐름을 판정한다. 메인이면 `references/korean-web-patterns.md`(`get_reference("korean-web-patterns")`) §2에서 한국형 메인 레시피를, 서브면 §4 서브 골격을 고른다. 페이지 유형은 Task Contract `pageType`과 `infoux.json` `pageTypes`에 함께 적는다.
2. `get_art_direction(profile)`로 표현 등급, 섹션 리듬 변주, 카피 톤을 확정하고, 실제 기관 용어·콘텐츠·사진의 출처(`contentSources`)를 확보한다. 등급 상향은 Task Contract의 `expression` 필드에 근거와 함께 기록한다.
3. 사용자의 핵심 과업을 한 문장으로 쓴다.
4. `references/krds-components.md`에서 재사용할 컴포넌트를 고른다.
5. `contracts/html-page-contract.json`으로 page shell과 section 구조를 확정한다.
6. 인터랙티브 위젯이 있으면 `design-widget` 절차를 함께 적용한다.
7. Task Contract의 필수 항목이 채워진 뒤에만 구현한다.

## 메인·랜딩이면 디자인 디렉션을 거친다

`pageType: main`이거나 랜딩이면 3번과 4번 사이에 `references/design-intelligence.md`(`get_reference("design-intelligence")`) 절차를 넣는다. 레시피는 무엇을 어떤 순서로 실을지를 정하고, 이 절차는 그것을 어떤 모양으로 보여 줄지를 정한다.

1. **컨셉** — 소재 5~7개, 컨셉 한 문장, 시그니처 장면을 쓴다(§2). 소재 가운데 하나 이상은 그 기관만 가진 구조가 있는 재료(시간·장소·수량·사물의 묶음)이고 실제 값을 확보한다(§2-1). 이름만 바꿔 다른 기관에 쓸 수 있으면 다시 쓴다.
2. **방향 라운드** — 두 축 이상에서 서로 다른 세 안의 첫 화면을 `docs/directions/`에 만든다. 정보 구조 축은 꼭 갈린다(§3-1). 세 안을 그 기관의 현재 메인·레퍼런스 사이트·통과 견본의 첫 화면과 나란히 놓고 바꿔 끼우기 검사를 넘긴 뒤(§2-4) 발주자가 하나를 고른다(§3-3). 레퍼런스에서는 값과 마감을 가져오고 첫 화면 문법은 가져오지 않는다(§3-4). 완성본을 먼저 만들지 않는다.
3. **디자인 계획** — `contracts/design-plan.md` 서식으로 `docs/design-plan.md`를 채운다. 블록마다 형식 id를 고르고(§6) 다이얼(`designDials`)은 Task Contract에 적는다.
4. **구현** — 섹션을 손으로 짓기 전에 블록 카탈로그에서 고른다. `list_blocks`(자리·형식으로 찾기) → `get_block`(「언제 쓰지 않나」와 필요한 콘텐츠 확인) → `compose_page`(공통 틀에 조립, 채울 자리 목록과 순서 점검) 순이다. 자리는 `contentSources`의 실제 내용으로만 채우고, 맞는 블록이 없는 자리만 프로젝트 블록으로 만든다. 계획한 색·서체를 헤더·버튼·탭·푸터까지 입힌다.
5. **렌더 비평** — 360·768·1024·1280·1440 전체 캡처와 1440·360 첫 화면 캡처를 찍는다(§8). 만든 에이전트는 자기 화면을 평가하지 않는다.
   1. 기계 검사 관문 — `npm run check`·`npm run check:contrast`·`npm run lint`와 렌더 실측(넘침, 터치 영역, 표제 비율, 글자 크기 가짓수)을 통과시킨다(§8-2).
   2. 별도 평가자(하위 에이전트·새 세션·다른 모델·사람)에게 캡처와 평가자 지시문(`get_reference("render-critique-evaluator")`)만 준다. 결함 찾기에는 비교용 다른 사이트 첫 화면 두세 장(`bigyo-*`)을 함께 준다. 디자인 계획과 의도 설명은 주지 않는다(§8-5).
   3. 평가자가 결함 문항 D01~D17에 예·아니오와 화면 근거를 답한다. 무거운 문항 「예」가 하나라도 있거나 일반 문항 「예」가 세 개 이상이면 불통과다(§8-3).
   4. 짝 비교 — 직전 최고안, 통과 견본(`get_reference("exemplars")`)과 나란히 놓고 「어느 쪽이 디자이너의 작품에 가까운가」를 자리를 바꿔 두 번 묻는다. 두 답이 같을 때만 판정으로 삼는다(§8-4).
   5. 고친 안은 직전 최고안을 두 번 모두 이길 때만 채택한다. 세 회차 연속으로 넘지 못하면 방향 라운드로 돌아간다(§8-6).
   6. 결과를 `docs/design-plan.md` 「비평 기록」에 평가자의 답 그대로 옮긴다(§8-9).
   평가자를 따로 둘 수 없으면 기계 검사만 하고 결함 후보를 적어 「사람 판정 필요」로 남긴다. 통과를 선언하지 않는다.
6. **사람 판정** — 평가자 통과는 확연히 못한 안을 걸렀다는 뜻이다. 운영자·발주자가 캡처를 보고 「승인」 또는 「불통과」를 정하고, 사유를 원문 그대로 적는다(§8-7). 「승인」이 없으면 `npm run check:release`가 실패한다.
7. **마감** — §5-8 일곱 항목을 확인한다.

서브·게시판·폼·검색 결과는 1·2번을 생략하고 사이트의 기존 계획을 따른다. 등급은 기능형~절제형 수위로 낮춘다(`art-direction.md` §1).

## 생성 원칙

- `main` 직계 자식은 목적 기반 `section`이다.
- 각 section은 `.container`와 접근 가능한 이름을 가진다.
- 정부·공공 요소는 `publicIdentity: required`일 때만 생성한다.
- 기존 section·컴포넌트 조합으로 해결할 수 있으면 새 block을 만들지 않는다. 다만 카탈로그 부품을 기본 모양 그대로 늘어놓는 것은 설계가 아니다. 형식은 `design-intelligence.md` §6에서 고르고, 카탈로그에 없는 모양은 프로젝트 블록으로 만든다.
- 구현 후 검사는 선택을 대신하는 단계가 아니라 마지막 확인 단계다. 검사를 통과한 화면이 좋은 화면이라는 뜻은 아니다.
