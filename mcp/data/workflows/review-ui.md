# review-ui

> **언제 쓰나** — INFOUX 기준으로 UI 구현을 리뷰하거나 규칙 준수 여부를 점검할 때 사용. 검사 결과만 나열하지 않고 Task Contract, 승인 패턴, 실제 구현의 차이를 우선 분석한다.

검사를 통과한 화면이 좋은 화면이라는 뜻은 아니다. 자동 검사는 규칙 위반만 잡는다. 리뷰는 Task Contract와 구현의 차이, KRDS 대조, 렌더 결과를 본다. KRDS와 다르면 KRDS를 따른다.

## 리뷰 전 확인

- Task Contract(`contracts/task-contract.md` 형식) 또는 작업 의도를 읽는다. 사이트 유형, 핵심 과업, 페이지 패턴, 재사용 컴포넌트, 위젯, 예외가 적혀 있어야 한다.
- 리뷰 대상 페이지가 메인·랜딩(`pageType: main`)인지 확인한다. 메인·랜딩이면 4번까지 한다.

## 리뷰 순서

### 1. 자동 검사 결과

```bash
npm run check
npm run lint
```

- 오류는 파일·줄·규칙 번호와 함께 그대로 적는다. 경고도 빼지 않는다.
- 하네스가 없는 프로젝트는 그 프로젝트의 `lint`·`build`·`test`·`a11y` 명령을 찾아 실행하고, 없으면 변경 파일을 직접 점검한다(`references/CONTRACT.md` §6의 최소 항목).
- 실행하지 못한 검사는 「실행하지 못함」과 이유를 적는다. 통과로 적지 않는다.

### 2. 배포 게이트 — `references/release-checklist.md`

- 필수 항목(접근성·과업 흐름·품질)은 전부 충족해야 한다. 하나라도 미달이면 불통과다.
- 접근성과 과업 흐름은 실제로 해 본다. 키보드만으로 주 과업을 끝까지 가고, 일부러 실패시켜 오류 안내와 복구 경로를 본다.
- 렌더는 360·768·1024·1280px 폭에서 본다. 넓은 화면 디자인이면 1440을 더한다. 1024에서 메인 메뉴와 전체메뉴가 바뀌는지 확인한다.

### 3. 납품 전 리뷰 — `references/art-direction.md` §9

- 안티패턴 색인(§10), 섹션 리듬, 카드화 필요성, 등급 강등, 상태 완결성, 실제 용어 정합, 이미지 라이선스를 항목별로 확인한다.
- 「KRDS 대조」 항목을 빠짐없이 본다 — 건너뛰기 링크 위치, 메인 메뉴 여는 방식, 캐러셀(5장 이내, 정지/재생 버튼이 첫 상호작용 요소), 텍스트 이미지, 진입 모달, 긴급 공지, 브레드크럼과 h1, 푸터 순서와 「개인정보 처리방침」, 탭, 버튼 레이블, 글자 크기·행간·자간, 클래스 이름.
- 구조와 마크업은 다음 기준으로 본다.
  - 시맨틱 HTML, ARIA 관계, 키보드, 포커스, 터치 영역 — `references/html-semantics.md`, `references/accessibility.md`
  - 기존 컴포넌트를 다시 쓸 수 있었는데 새로 만든 곳, 이유 없는 wrapper — `references/krds-components.md`, `references/html-semantics.md` §6.6
  - 토큰, BEM, 클래스 이름, Tailwind v4, CSS layer — `references/forbidden-patterns.md`, `references/class-naming.md`

### 4. 메인·랜딩 — `references/design-intelligence.md` §7·§8

메인·랜딩이 아니면 건너뛴다.

1. `docs/design-plan.md`가 있고 컨셉, 방향 라운드에서 고른 안과 이유, 블록별 형식이 적혀 있는지 본다.
2. 360·768·1024·1280·1440 폭으로 전체 페이지를, 1440·360 폭으로 첫 화면을 캡처한다(§8-1). 코드를 읽고 평가하지 않는다. 캡처를 본다.
3. 기계 검사 관문(§8-2)을 먼저 본다. 불통과면 평가하지 않고 그 결과를 보고한다.
4. 리뷰하는 에이전트가 이 화면을 만들었으면 평가하지 않는다. 캡처와 평가자 지시문(`get_reference("render-critique-evaluator")`)만 별도 평가자에게 넘긴다(§8-5). 만든 대화를 모르는 리뷰어는 스스로 평가자가 될 수 있다. 그때도 디자인 계획의 컨셉·의도 설명은 평가를 마친 뒤에 읽는다.
5. 결함 문항 D01~D17에 예·아니오와 화면 근거를 적는다(§8-3). 점수를 매기지 않는다.
6. 통과 견본이나 직전 최고안의 캡처가 있으면 자리를 바꿔 두 번 짝 비교한다(§8-4).
7. §7 서명을 센다. 전형 조립(§7-1)은 한 개 이하, 템플릿 장식(§7-2)은 없어야 한다.
8. 결과를 계획의 「비평 기록」 칸에 회차로 남긴다(§8-9). `npm run check:release`가 이 기록을 읽는다.

D01(어느 기관인지 알 수 없다)이나 D03(첫 화면이 기본 틀 그대로다)이 「예」면 부분 수정을 권하지 않는다. 방향 라운드(§3)로 돌아가라고 보고한다. 평가자 통과는 확연히 못한 안을 걸렀다는 뜻이므로, 사람 판정이 비어 있으면 「사람 판정 필요」라고 보고한다.

## 결과 보고 형식

발견 사항은 사용자 영향이 큰 순서로 적고, 각각 파일과 위치, 근거 규칙 또는 문서 절, 고치는 방법을 붙인다. 검사 통과만으로 설계 의도가 맞다고 결론 내리지 않는다.

