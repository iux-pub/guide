# INFOUX 디자인 계획

메인·랜딩 페이지를 만들기 전에 이 서식을 프로젝트의 `docs/design-plan.md`로 복사해 채운다. 판단 방법은 `references/design-intelligence.md`가 정한다. 납품 검사(`npm run check:release`)는 메인 페이지가 있는 프로젝트에 이 파일과 아래 일곱 제목, 별도 평가자의 비평 기록과 사람 판정이 있는지 확인한다.

서브·게시판·폼만 만드는 작업에는 쓰지 않는다. 사이트에 이미 계획이 있으면 그것을 따른다.

방향 라운드 단계에서는 「컨셉」과 「방향」 칸, 「원칙」 아래 「마감 기준」 표만 채운다(스케치도 그 값으로 짓는다). 방향 표의 「바꿔 끼우기」 칸은 세 안을 다른 사이트 첫 화면과 나란히 놓고 본 결과다(design-intelligence §2-4). 세 안은 컨셉이 서로 다를 수 있으므로 「방향」 표에 안마다 컨셉 한 문장을 적고, 안을 고른 뒤 「컨셉」 칸을 고른 안의 것으로 확정한다. 「색」 이하 칸은 그 뒤에 쓴다.

비평 기록을 적는 법:

- 평가자는 화면을 만든 에이전트가 아니다. 캡처와 평가자 지시문(`contracts/render-critique-evaluator.md`, MCP `get_reference("render-critique-evaluator")`)만 받은 하위 에이전트·새 세션·다른 모델·사람이다. 디자인 계획과 의도 설명은 평가자에게 주지 않는다.
- D01~D17 줄과 짝 비교 줄은 평가자의 답을 고치지 않고 옮긴다. 두 평가자가 갈려 셋째 평가자의 다수결로 정한 문항은 `D07 아니오(다수결 2:1) — <폭과 위치, 본 것>`처럼 답 바로 뒤 괄호에 적는다.
- 직전 최고안이 없는 1회차는 「짝 비교 1·2」 줄을 빼고 「채택: 첫 안」이라고 적는다. 통과 견본이 없으면 디비컷 기관/단체 평점 상위 사이트를 같은 폭으로 찍어 견본 자리에 쓰고, 꺾쇠 자리에 사이트 이름을 적는다(design-intelligence §8-4). 견본 비교는 건너뛰지 않는다. `견본 비교: 견본 없음`은 옛 서식이다 — 1~6회차가 이렇게 건너뛰는 동안 실제 기관 사이트보다 앙상해진 것을 아무도 잡지 못했다.
- 평가자를 따로 둘 수 없으면 `평가자: 분리 못 함`이라고 적고, D 줄에는 「예」로 보이는 결함 후보만 적으며, 짝 비교 줄은 뺀다. `사람 판정: 필요`로 두고 통과라고 적지 않는다.
- 사람 판정은 운영자·발주자가 한 말을 그대로 옮긴다. 에이전트가 대신 채우지 않는다.
- 「짝 비교 1·2 차원」 줄은 평가자 과제 2의 차원 답을 옮긴다. 판정은 「짝 비교 1·2」 줄의 전체 답으로만 한다. 두 답이 갈렸으면 어느 차원에서 갈렸는지 이 줄로 본다(design-intelligence §8-7).
- 「계획 대조」 줄은 과제 1·2를 맡지 않은 평가자의 과제 3 답이다. 안 보인 문장은 고쳤는지, 계획에서 지웠는지 함께 적는다(design-intelligence §8-3).
- 「다음 회차」 줄은 회차를 마칠 때 다듬기와 전환 가운데 고른 것이다(design-intelligence §8-6).

## 검사가 보는 것

1. 일곱 제목(`## 컨셉`·`## 방향`·`## 색`·`## 서체`·`## 레이아웃`·`## 원칙`·`## 비평 기록`)이 모두 있다.
2. 서식의 꺾쇠 자리값(`<대상>` 같은 것)이 남아 있지 않다.
3. 비평 기록은 채택이 「첫 안」이나 「교체」인 마지막 회차(지금의 최고안)를 읽는다.
   - `평가자:` 줄이 있고 만든 에이전트가 아니다. 「자기 채점」「자체 평가」「만든 에이전트」 같은 표기는 불통과다.
   - `기계 검사:` 줄이 「통과」다.
   - D01~D17 결과가 있다. 무거운 문항(D01~D07·D17) 「예」가 0개, 일반 문항(D08~D16) 「예」가 2개 이하다.
   - 짝 비교가 순서를 바꿔 두 번 기록됐다(`짝 비교 1·2` 또는 `견본 비교 1·2`). 「교체」는 이번 안이 두 번 모두 우세할 때만 된다. 통과 견본이 두 번 모두 우세하면 불통과다.
   - `채택:` 줄이 있다.
   - `사람 판정:` 줄이 있다. 납품 검사(`npm run check:release`)에서는 「승인」이어야 하고, 「대기」「필요」나 빈 칸이면 오류다.
4. 옛 「합계: NN/20」 서식은 받지 않는다. 검사가 새 서식을 안내한다.

개발 중(`npm run check`)에는 위 항목이 경고이고, 납품 검사에서는 오류다.

검사는 절차를 밟았는지만 확인한다. 평가자 통과는 확연히 못한 안을 걸렀다는 뜻이고, 화면이 실제로 좋은지는 사람이 본다.
